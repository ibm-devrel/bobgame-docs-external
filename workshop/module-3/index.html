An Experimental Framework for Production Agents

Test vs. prod, verification loops, and comparing agent runs systematically, all the way to loop engineering.

Present full screen ↗Click the slides (or ← →) to advance · S speaker notes · F fullscreen
Learning Objectives

By the end of this module you will:

  • Know how to give an agent guardrails and a good objective
  • Understand why building an agent with an agent has limits
  • Know how to set up a "test vs. prod" split for agents, and why the game has 6- and 26-city maps
  • Understand what a verification loop looks like for agents outside of coding, and why it's the only way to solve these puzzles
  • Be able to run, log, and compare agent experiments systematically with Bob

Goal: treat your agent like a production system: change one thing, measure it, and keep what works.

The Scene

By now you've changed your agent a few times. You've given it a verification loop, a map, and a way to fix its own notebook. So: is it better?

So far, you've been able to tell by looking at how fast it ran, or maybe noticed a few particular entries from the investigator agent that made you concerned about its behavior. If you had a great run, you might think your work is done.

As we saw in Module 2, agents are stochastic: the same agent can have a great run and a terrible one back to back. You can't draw conclusions based on one run.

This is just as true in real-world agents. A few good runs aren't enough to make a determination. In this module, we'll talk about how to set up an experimental framework around your agents.

The Concept: An Experimental Framework for Production Agents

Prompting the agent and giving it rules

The most direct way to change how an agent behaves is its prompt. In the game, that's build_system_prompt: it tells the player agent who it is, what it's trying to do, and the rules it should follow at each city ("check your notebook first", "don't revisit cities").

It's worth being clear about what a rule in a prompt actually does. LLMs will treat those rules as guidelines. More advanced agents will follow them more often; less advanced agents will not.

A longer prompt with more rules doesn't fix this. In fact, each rule added gets less of the model's attention, and unless everything is abundantly clear, contradictions will likely emerge.

Consider the rules in the current prompt. Which ones actually require semantic judgment? Are there any that could be exposed using deterministic algorithms to help the agent stay on task?

  • "Don't travel to a city you've already visited" isn't really a semantic question. Your code can compute the unvisited cities from the orientation and focus the agent's attention there.
  • "Decide which lead to trust when two of them disagree" does need a semantic judgment.

This introduces a framework for building our agents: we will restrict the agents themselves to only be making semantic decisions where appropriate.

Creating a verification loop

The agent already knows it is supposed to find the drive. However, without being able to confirm its progress, the agent won't know whether it's getting closer or further away from its goal.

The game is actually scored on three things, in order:

  1. How many evidence words the agent correctly records in its notebook (counted even if it never finishes; crossed-out entries don't count)
  2. How fast it runs
  3. Whether it opens the safe at the finale (an agent that does this rises straight to the top)

In our agent design, we need to do three things:

  • Clearly convey that objective
  • Articulate a strategy for solving it
  • Tell the agent how to check its progress

How might we use the existing facilities provided in the game - the notebook, the tools, the ability to talk to the NPC - to check progress more effectively?

Using Coding Agents

When you prompt coding agents, you are also giving them objectives. "Make my agent faster" will get you a change. "My agent revisits cities in most runs. Find out why from the logs, and establish a strategy for detecting cycles using the notebook" should get you much better results.

Building agents with agents

You've been building an agent with another agent: Bob writes the player agent.

But since Bob is an LLM too, it has the same issues.

  • Bob can't see the dashboard either. It doesn't know how fast your last run was unless you tell it, or unless it reads the logs.
  • Bob doesn't know the codebase. Installing something like codegraph will let it "see" how the symbols interact.
  • Bob will tell you a change worked. It defines a "working" agent as one that compiles and runs, not one that makes specific types of improvements. How can you design tests for the actual strategic improvements you want to see?
  • Bob drifts. Ask for one fix, and you may get three other "improvements" along with it. When two of those interact, you won't know which one made the difference.
  • Bob gets distracted. If you spend too much time talking about your plans, and then immediately start implementing, Bob may implement some superset of the changes you requested and the changes you talked about that one time.

The things that keep Bob on track are the same things that keep any agent on track:

  • Rules: AGENTS.md is Bob's system prompt for this repo. Our version tells it to start from the logs, to only change player_agent.py, and not to hardcode anything from the 6-city game. You'll add to it in this module.
  • Testable changes: the logs from your runs. Ask Bob to start from them, every time, and compare with prior runs.
  • Checks: the behavior tests in tests/test_player_behavior.py, and the game itself.
  • Small changes: one change per run, so you can tell what changes helped you make progress.

Test vs. prod

The game you've been running has 6 cities. Your submission isn't judged on that game. It's judged on a 26-city game that you never see. The city names are different, the NPCs are different, the evidence words are different, and the map is bigger and shaped differently.

That's on purpose. In machine learning, this is the split between training data and test data. If you tune your agent against the 6-city game too closely, it overfits: it gets very good at the game you can see, and falls apart on the one that counts. An agent that hardcodes the evidence words from the 6-city game will fail fast on the 26-city one.

The rule of thumb: general truths transfer. Specific truths don't. "Leads point to other cities" is true in both games. "The filesystem tool finds the lead in London" is not.

This applies to every agent you'll build, not just this one. Say you're building an agent that triages support tickets. If you write the prompt by looking at last month's tickets, then test it on the same tickets, it will look great. Test it on this month's instead. Keep a set of cases that you (and Bob!) never look at while you're tuning, and only use them to check. If you let Bob read your test cases, it will very helpfully tune your agent to pass them.

Watch Bob for this

Bob can see the 6-city game's data. If it starts writing city names, NPC names, or evidence words into player_agent.py, that's overfitting. Our AGENTS.md tells it not to, but it's a rule in a prompt, so that doesn't guarantee that it won't.

Agents are non-deterministic, so experiment

Since one run tells you very little, you need more than one. The habits that make this work are the ordinary habits of running an experiment:

  • Change one thing at a time. If you change the prompt and a hook and the tools in the same run, you won't know which one mattered.
  • Run each version more than once. Two runs is the bare minimum. Three is better. You're looking for the typical result, not the best one.
  • Write the results down. For each version: what you changed, the time, how many cities it visited, how many evidence words it recorded, and whether it finished.
  • Keep the version that wins, and be able to get back to it. Bob keeps checkpoints, but also consider making git commits as you go along so that you can keep track of its behavior.

One more thing you can change: the model.

The game uses one LLM for all of its agents: the narrator, the NPCs, and the player agent. Booths usually run something small and fast. A bigger model (say, Opus instead of Sonnet or Haiku) is better at reasoning through messy text and holding more of the situation in mind at once. It's also slower and costs more, and this game scores speed.

Can a bigger model solve the problem where a smaller one can't? Sometimes. A bigger model can make up for a weak prompt. But it can't see information it was never given. If the agent doesn't have the map, Opus doesn't have the map either. Most of what you did in Modules 1 and 2 helps a small model more than a big one, and that's the trade worth knowing: a bigger model or a better harness. In production, a better harness is usually cheaper.

Verification loops beyond coding

In coding, verification loops are everywhere, and we mostly take them for granted: the compiler, the type checker, the test suite, CI. A coding agent writes code, runs the tests, sees what failed, and tries again. That's a big part of why coding agents got good before other kinds of agents did.

Outside of coding, you usually have to build the loop yourself. It's the same shape every time: the agent does something, something outside the agent checks the result, and the agent gets told what was wrong.

  • In this game: enter_evidence_words tells the agent how many of its words were right.
  • In Minecraft: each step toward the Ender Dragon either happened or it didn't, and the agents were able to check.
  • In math: Lean checks whether a proof is valid.
  • For a support agent: did the customer reopen the ticket?
  • For a research agent: do the papers it cited exist, and do they say what it claims they say?

These real-world problems need to be structured the same way in order for an agent to be able to make progress without human intervention.

The agent has no map of the world, it doesn't revise its beliefs, and it's stochastic. It can't reliably notice that it's wrong by thinking harder about the same information. The signal that it's wrong has to come from outside the model.

There are two loops in this workshop. The inner loop is the player agent checking itself at the safe.

The outer loop is you and Bob: change the agent, run the game, read the logs, change it again. Everything in this module is about making the outer loop work.

Step 1: Make every change traceable

Before you start running experiments, make sure you can tell your versions apart and get back to any of them.

Exercise · Commit as you go

Ask Bob to commit after every change, and to add that rule to AGENTS.md so it keeps doing it.

Bob · Agent modeAdd a rule to AGENTS.md: after every change to player_agent.py, make a git commit with a short message that says what changed and why. One change per commit. Then commit the current state of player_agent.py so we have a starting point.
Commits vs. checkpoints

Bob also saves checkpoints as it works, and you can roll back to one from the chat. That's useful for undoing a change Bob just made. But checkpoints belong to Bob's session, and might roll back the conversation as well.

Commits are in your repo's history: they have messages, they stick around, and you can line them up with your game logs.

For this game, merge to "main" before you submit please.

You might also connect each game log to the version of the agent that played it. The game writes a log to logs/ for every run, with a start_time in it. If you want, you can change the game engine code to do this: It won't change how it runs on the server, but it lets you set up a local loop.

Bob · Agent modeWrite a small script in scripts/ (analysis only, not part of my submission) that goes through every log in logs/, finds the most recent git commit before the log's start_time, and prints one row per run: the commit hash and message, the run time (last_updated minus start_time), the status, the number of cities visited, whether it revisited any city, and the number of evidence words recorded. Don't change player_agent.py.

Step 2: Run multiple games

Exercise · Iterate

This is the outer loop. Repeat it as many times as you have time for:

  1. Pick one thing to change. Start from the logs: ask Bob what's going wrong most often.
  2. Have Bob make the change and commit it.
  3. Hit New Game, re-choose your tools, and let it run.
  4. Run the same version again.
Bob · Ask modeRead my most recent logs in logs/. What is the most common problem across these runs (not just the last one)? Suggest one change to player_agent.py that would fix it, and tell me what I should see in the next run if it works.

Step 3: Compare runs

Exercise · What changed, and did it help?

Run your script from Step 1, then ask Bob to read it with you.

Bob · Ask modeRun the comparison script in scripts/ and show me the table. Group the runs by commit. For each commit, what was the typical run time, and did it get better or worse than the commit before it? Which change made the biggest difference? Are any of the differences small enough that they could just be run-to-run variation?

If a change made things worse, roll it back:

Bob · Agent modeRevert the commit that made the run time worse, and commit the revert.

The dashboard only shows you the current run, so the comparison has to come from your logs. That's normal for agents in production, too: the useful view is the one you build across many runs.

Step 4 (Optional): Try a different model

Exercise · Bigger model, same agent

Pick your best commit. Switch the model (we have claude-haiku-4-5 and claude-sonnet-4-6 available), change nothing else, and run it twice. Then switch back.

Did the bigger model finish where the smaller one didn't? Was it faster or slower? What did it do differently in the logs?

Think about it

If the bigger model did better, what was it doing that the smaller model couldn't? Could you get the smaller model to do the same thing with a hook or a rule?

Step 5 (Advanced): Loop engineering

Let's get meta. Give Bob a target and let it run the outer loop on its own.

Bob · Orchestrator modePlease keep making modifications until my time is driven down to 120. Use subagents.
Think about it

What happened? Where did Bob's loop help, and where did it go off the rails? Did it overfit to the 6-city game? How did it decide whether a change worked?

What's Working

Over the four modules, you've built up a full set of tools for working with agents:

  • Module 0: using Bob's modes to change an agent, and checking the result in a new game
  • Module 1: hooks that pull facts out deterministically, and a verification loop at each city
  • Module 2: a map for an agent that can't see one, and a way to revise what it believes
  • Module 3: an experimental framework: one change at a time, every change committed, every run logged, and versions compared on evidence instead of feelings

None of these are specific to this game. The player agent is a small version of every agent you'll build: it can't see the whole world, it's stochastic, and it needs something outside itself to tell it when it's wrong.
