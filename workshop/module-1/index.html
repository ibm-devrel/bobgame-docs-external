The Scene

Deep Blue Drive Heist is a difficult challenge for AI agents. Of the couple hundred people who've played it this year, only about 1 in 10 have built an agent that can solve the full 26-city game on its own.

The game is built on and run by agents, which by their nature act non-deterministically: you can't count on them to repeat the same behavior on a new run.

In this module, we'll use the game's agent to help illustrate basic concepts about agents. (If you're already fairly familiar with what agents are and what they can do, feel free to jump to Module 2.)

What is an Agent?

An agent is a software system that uses large language models (LLMs) to pursue goals, break down problems, and perform tasks for developers and automation.

While many possible agent types exist, most AI agents today use some form of the ReAct loop.

The agent in this game uses elements of the ReAct loop, but, importantly, it never takes feedback from the human player. It is also limited in when and how it can respond, and what information is available to it when it does.

Refining agents to solve complex problems requires verification loops, specific targets to reach, and an environment where the agent can improve iteratively. This is true of all AI agents. (We'll talk more about how to think about an AI agent's capabilities in the next module.)

Agents in Deep Blue Drive Heist

There are two primary types of agents in Deep Blue Drive Heist:

  1. IBM Bob, the coding agent you talk to for improving the player agent. Bob is a general-purpose ReAct-based agent in a coding harness designed to help you solve software development tasks.
  2. The player agent, which plays the text adventure game and is the agent Bob is helping you change. The player agent is NOT a general-purpose agent, and can only interact with, and react to, elements of the game itself.

The player agent is built on LangGraph (part of the LangChain ecosystem), which means it will only respond at specific times in a deterministically defined workflow. This sets it apart from the typical general-purpose agent.

How a Typical General-Purpose Coding Agent Works

Most coding agents and general-purpose agents you may have encountered (Bob, Claude, ChatGPT) follow one pattern: a user sends a message, and the LLM receives it. The LLM calls whatever tools it needs, and the results of each tool call are appended to the thread. Once it has what it needs, the LLM puts together a response for the user.

This forms the ReAct loop that defines a general-purpose agent:

This loop exists inside what's known as a harness: the extra features that allow advanced behavior and advanced control of AI coding agent sessions.

A typical agentic harness will contain the following:

A user who wants to control how a coding agent behaves usually edits configuration files that change how the harness behaves. Examples might include:

  • System prompt: In addition to the system prompt provided by the harness itself, these are extra instructions from the user on how to behave.
  • Skills: Folders of instructions on how to perform certain tasks, often written in Markdown, sometimes containing executable tools to make available to the agent.
  • Tools: Functions that the agent is allowed to call during its run. These are usually MCP servers, but not always.
  • Memory: Often built into the harness, but occasionally provided by the user. This allows the agent to save information that it classifies as relevant to potential future sessions. Memories are retrieved using hooks on the agent's messages, usually based on semantic similarity, to give the user the impression that the agent "remembered" their last conversation.
  • Filesystem access: Through tools, typical coding harnesses make the local filesystem available to general-purpose agents.

Results from tool calls, memories, and skills all become part of the conversational context. Users typically control a single session, and choose to compact, clear, or start a new session when they find that the session is too long. In most coding harnesses, messages are append-only, and form a permanent part of the record.

How Does the Deep Blue Drive Heist Player Agent Differ?

Our agent is still using a ReAct loop, but it is different from an agent in a coding harness in the following ways:

  • There are no skills.
  • The set of tools is pre-selected using the MCP Server Shop at the beginning of the game.
  • Its "notebook" is its only memory. It gets one free-form note, but most of what it records has to fit a specific shape, which helps it solve the puzzle: a lead, for instance, must be written down as a chess piece, the finding it came from, where it was seen, and the city it points toward.
  • The other things the agent can do - speak to NPCs, interact with its notebook, or travel to new cities - are also seen as tools by the agent.
  • There is no local filesystem access available to this agent: it can't write anything down outside the game world, access the internet, or do anything else outside the game.
  • The session context gets reset at each city. Only the notebook remains as memory available to the agent.

The human player never speaks. Instead, the other messages in the game come from two other agents: the Narrator agent and the NPC agent, each of which is responsible for speaking only when it's its turn. Neither agent may speak up in reaction to anything else that happens in the game log unless the game specifically calls for it.

Although the game's code calls the narrator and the NPC "agents", they aren't truly agentic: they can't make arbitrary tool calls and then respond to the results.

Is the player agent in a harness?

Maybe. The definition of "harness" floating around the industry is a little underspecified. Usually, people are referring to a ReAct-style agent that has tool access to a filesystem and the internet and is set up to respond to general-purpose requests, and the "harness" they're referring to is anything else that directs its behavior. For this reason, this particular setup stretches the definition of "harness" beyond its usual intent.

Further reading: The Anatomy of an Agent Harness, and Agent Harness Engineering.

This setup establishes a hybrid deterministic / semantic workflow. Each agent's LLM is called only at specific times. None of them can respond to just anything in the record that it considers worth responding to, the way coding agents and chat agents usually can.

The Player Agent and Hooks

In the game, when the narrator agent, NPC agents, and tools produce messages, the player agent always sees each message as it is. But you get a chance to run your own code on each one, and add a note of your own after it.

This gives the player / software developer some control over the agent's understanding of the world. These are Python methods called hooks:

  • highlight_narrator_message, highlight_npc_message, and highlight_tool_result run once on each message from that source. Whatever text a hook returns is added to the conversation as [Highlight on <source>]: <your text>. Return None to add nothing.
  • briefing runs right before each of the agent's turns. Whatever it returns is shown as [Briefing]: <your text>.

Hooks can't hide or change a message: they can only add to it. By default, every hook returns None, so the agent sees nothing extra. If the player chooses, they have an opportunity here to use deterministic code to assist the agent in making a decision about how to respond next.

Every hook (and the system prompt) also gets the orientation: read-only facts about where the agent is, like the cities it can travel to (connections), the cities it has visited (visited_cities), and every route it has seen so far (known_routes). Hooks can also read the agent's notebook (self.notebook), but they can't write to it.

For instance, the agent's hooks could:

  • Pull the connecting cities out of the narrator's scene into a short list
  • Count the number of times a chess piece shows up in a tool result
  • Total the number of leads pointing in each direction
  • Brief the agent on the state of the game (how far it has traveled, which cities it's visited) before its turn
  • Point out which connected cities haven't been visited yet

The hooks in this game allow players to use deterministic code to highlight information and direct the LLM’s attention to it.

Hooks in Coding Agents

Some coding harnesses allow these sorts of hooks as well - running an extra function on a tool result before it reaches the agent. (Unlike the game's hooks, these can usually change or hide what the agent sees.) These can be used for many purposes, but are most commonly used to implement guardrails, like PII (Personally Identifiable Information) filtering, filtering sensitive information like passwords, and suppressing confidential information the LLM shouldn't have in its logs.

The Game System

The game engine itself is based in LangGraph, a flexible agent orchestration framework that allows you to develop arbitrary agent interactions.

The game engine builds a LangGraph StateGraph for every city visit. This graph differs from a usual ReAct loop graph. It has four node types:

  • The narrator
  • The player
  • The tools
  • The NPCs

Each node appends messages to a shared messages list. The hooks do not run when the narrator or NPC produces a message. They run when it's the player agent's turn, just before its LLM call, and their highlights come after everything new since its last turn. This means that the agents do not just chime in whenever they want. The narrator does an intro, the NPC says hello, and the actions of the player agent determine the direction of the conversation. The other agents only respond in reaction to the player agent’s behavior.

The record of messages is reset any time the player agent uses the travel_to function. The player agent itself is created fresh in every city, too, so nothing your code keeps on self carries over. Then, the narrator speaks again, the NPC says hello, and the loop repeats itself.

In the finale city, the player agent is given an extra tool - enter_evidence_words - and the NPC agent is given extra instructions to help the player agent navigate the final test.

The enter_evidence_words tool at the end lets the agent engage in a verification / validation loop. When it reaches the safe, it can check the information in its notebook so far, validate how much is correct, and when it discovers that it has the wrong answers, make a new plan.

What's In Each Message

Take a look at the three message sources that the agent can pick up on:

  • Narrator: Looks unstructured, but there's actually structure to it.
  • NPCs: Largely unstructured, but often give hints. Can you identify those hints deterministically?
  • Tool results: Is there a structured way to extract the right answers?

The three sources look unstructured or random, but each follows a structure, which means you can extract the facts that matter in Python rather than hoping the model notices them.

  • Narrator: One structured LLM call per city, delivered as three entries - atmosphere, a bulleted list of room objects (one bullet per object your tools can examine), and a bulleted list of exits (one bullet per connected city).
  • NPC: Driven by a hints array inside each city's story file. At an evidence city, the NPC is explicitly instructed to reveal the evidence word clearly and make sure the player knows it's an evidence word to remember. At other cities, it drops destination city names in phrases like "head to Stockholm" or "traces lead to..."
  • Tool results: The most structured. The engine formats every result as === Tool Name results ===, then --- Finding N [finding_id] ---, then the content block. The finding ID is what the agent passes to show_finding and record_lead.

MCP Tools

An MCP server (Model Context Protocol) connects AI applications and agents to external tools, APIs, and services. Think of it as a "plugin" for AI models that lets them access external systems and data. MCP servers for standard coding agents can wrap an existing API, or may be provided by a particular service you want to connect your coding agent to.

When you play Deep Blue Drive Heist, you choose MCP servers to support your player agent before it starts the game. These MCP servers do not enable the agent to interact with the real world, but instead, help the agent reach the game world. (Even in fake worlds, LLMs still can't act on their own without code to help that happen.)

Tools are exposed to the LLM using JSON:

{
  "name": "filesystem",
  "description": "Search this resource. Returns ALL available documents at once — calling again will not yield new results.",
  "input_schema": {
    "type": "object",
    "properties": { "query": { "type": "string", "default": "search" } }
  }
}

MCP servers, both in the real world and in the agent world, are surfaced to the LLM as tool calls. Under the hood, that looks a lot like code. A typical call to an MCP server from an LLM will look like:

{
  "role": "assistant",
  "content": [
    { "type": "text",
      "text": "Marcus is giving me clear leads… Let me search the PS/2 terminal's filesystem first to see what evidence is there." },
    { "type": "tool_use", "id": "toolu_01…", "name": "filesystem",
      "input": { "query": "search" } }
  ]
}

And then the response comes back, also as a JSON blob:

{
  "role": "user",
  "content": [
    { "type": "tool_result", "tool_use_id": "toolu_01…",
      "content": "=== filesystem results ===\n\n--- Finding 1 [chess_board] (terminal_display) ---\n  ♜♞♝♛♚♝♞♜ …\n  Black just played b7→b5\n\n  YOUR MOVE\n  1. Nf3 — Toronto\n  2. d4  — Dublin\n …\n=== End of filesystem — 1 finding(s) total. This is everything available. ===" }
  ]
}

The MCP server "investigation tools" that you pick will enable your agent to be able to access certain databases, files, or findings in the game that may help with its search for the drive.

Every tool result either adds atmosphere to the investigation or conveys a particular lead. All leads in the game are a combination of a chess piece and a city. The city reference is usually slightly obscured - Paris might be "The City of Light". Since LLMs are semantic processing engines, they can usually decode these references.

These references are embedded in normal-looking text, like commit logs, so that it appears that the Architect has hacked into the servers and left leads behind.

The game is balanced so that any combination of MCP servers provides enough leads to win. So while it's important to understand the role of the MCP servers, it matters less which ones you select for your agent's mission.

Agent Memory: The Notebook

As your agent finds information that it thinks may be relevant, it will store it in its Investigator's Notebook. The agent writes to the notebook with its notebook tools (record_evidence, record_lead, take_note, revise, and cross_out), and can read it back with check_notebook(). Your code can read the notebook through self.notebook, but only the agent's own tool calls can change it.

Because the agent starts a new LLM conversation at every city that it visits, the notebook is important as the persistent memory that the agent can refer to. It serves as the context it needs to make its next decisions.

Coding agents can usually store arbitrary Markdown-shaped memories in whatever format they like. The tool calls for the player agent's memory are more restricted. It gets one freeform note, but most of its entries are in the shape of particular leads and evidence words that it will need to solve the puzzle. It can also correct an entry (revise), mark it as confirmed, or strike it out (cross_out). This prevents the agent from using its memory as a fun place to put its hallucinations about the storyline.

Limitations of Agents When Problem-Solving

If the agent has all these tools and memory at its disposal, why can't it just simply solve the game?

AI models can produce different outputs for the same input: agent responses are non-deterministic and are rarely the same twice. As a result, the player agent often won't respond the way players want it to after an improvement, which makes it hard to tell whether an intended change is taking effect.

Specific, intentional prompting of your AI coding agent becomes important for working around non-determinism. Detailed prompts help the coding agent stay on task.

When prompting Bob, be precise and include as many relevant details about your problem as you can. Answers will still be non-deterministic, but specific prompts make the results more consistent.

Hit the green “New Game” button to test your changes. Check whether the total time the agent takes to find the drive is going down on the dashboard. You may also use IBM Bob to analyze your game logs to get a cohesive analysis of your agent’s current performance.

Bob · Ask modeCompare my current agent’s performance with previous runs of the game. What has improved?

What's Working

Your player agent should now have a verification loop at each city, where the hooks – highlight_narrator_message, highlight_npc_message, highlight_tool_result, and briefing – extract signals deterministically. They each bring the right details directly to the agent's context window rather than waiting for the model to pick out information itself.

What's Still Hard

The agent is still operating with blind spots – though it has a verification loop, it arrives at each city with no memory of anything but what exists in the notebook. It cannot see the map, does not know how long it's taking to find the drive, and implicitly trusts a notebook that may be riddled with misinformation.
